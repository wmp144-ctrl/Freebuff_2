# گزارش اصلاح موتور مانیتورینگ و تضمین صحت عملکرد

موتور مانیتورینگ NetWatch (`server/engine.js`) بازبینی و بازسازی شد. تمرکز این
بخش روی چهار موضوع بود: **یک موتور در هر لحظه**، **تفکیک قطعی واقعی از خطای
داخلی**، **مقاوم‌بودن به بار و Crash** و **بازیابی درست وضعیت پس از Restart**.

- اجرای این بخش: `npm run test:engine` (۳۹ آزمون) — همه سبز
- آزمون کامل پروژه: `npm run verify` — سبز
- گزارش بار ۱۰۰۰ تجهیز: `npm run load` → `data/load-report.json`

## ۲. تغییرات اصلی

| فایل | نقش |
| --- | --- |
| `server/engine.js` | قفل رهبری با Lease (پیش‌تر موجود، تکمیل‌شده با چرخهٔ حیات)، تفکیک خطای داخلی/شبکه، مهلت سخت پروب، شاخص Scheduling Lag، هشدار مستقل موتور، `recoverState`، `restart`، حذف `catch` بی‌صدا در چرخه |
| `server/leader.js` | قفل Lease با TTL، تمدید، آزادسازی و گزارش مالک (بدون تغییر رفتاری) |
| `server/db.js` | ستون‌های `samples.scheduled_at`/`started_at`، تجمیع قطعی‌های باز تکراری و ساخت قید یکتای `outages(device_id) WHERE open = 1`، پیش‌فرض عملیاتی `engine_mode = 'auto'` |
| `server/routes/ops.js` | `engine/control/:action` با `start`/`stop`/`restart`/`recover`، خلاصهٔ هشدارهای موتور در `/api/engine/status` |
| `server/engine-cli.js` | خاموش‌سازی مرتب با `SIGINT`/`SIGTERM`، نمایش خطای داخلی و تأخیر زمان‌بندی در گزارش دوره‌ای |
| `server/tests/unit/engine-*.test.mjs`، `server/tests/integration/engine-*.test.mjs` | ۲۰ آزمون تازهٔ موتور |

### چرخهٔ حیات استاندارد

| عملیات | مسیر | رفتار |
| --- | --- | --- |
| Start | `POST /api/engine/control/start` / `engine.start()` | گرفتن قفل، `recoverState()`، تجمیع روزهای جامانده، شروع چرخهٔ ۲۵۰ms |
| Stop | `.../stop` / `engine.stop()` | توقف چرخه، لغو هشدارهای معوق، آزادسازی فوری قفل |
| Restart | `.../restart` / `engine.restart()` | Stop → تخلیهٔ بررسی‌های در جریان → Start (وضعیت تجهیزات و قطعی‌های باز حفظ می‌شوند) |
| Recovery | `.../recover` / `engine.recoverState()` | اصلاح سازگاری داده: پیوند مجدد قطعیهٔ یتیم، پاک‌کردن ارجاع شکسته، تجمیع قطعی باز تکراری |

## ۳. سناریو ۱ — قطع شبکه، هشدار و بازگشت

آزمون: `engine-detection.test.mjs` + بخش زنجیرهٔ TCP در `server/tests/smoke.mjs`.

| گام | نتیجهٔ اندازه‌گیری‌شده |
| --- | --- |
| دو شکست متوالی (آستانه = ۳) | وضعیت `online` می‌ماند، صفر قطعی، صفر هشدار |
| شکست سوم | وضعیت `offline`، **دقیقاً یک** قطعی باز، **دقیقاً یک** هشدار `critical`، `current_outage_id` ثبت می‌شود |
| یک موفقیت پس از قطعی | تجهیز همچنان `offline` (تنظیم `successes_for_online = 2` رعایت می‌شود) |
| دو موفقیت | وضعیت `online`، قطعی بسته با `duration_sec >= 1`، هشدارهای قطعی `resolved`، یک هشدار `recovery` |
| افت کیفیت بدون قطعی | تأخیر ۴۰۰ms با آستانهٔ ۱۰۰ms ⇒ وضعیت `warning` و یک هشدار `latency`؛ تجهیز در دسترس هیچ قطعی‌ای باز نمی‌کند |

نتیجهٔ مهم این بخش: «خطای شبکه» تنها مسیری است که می‌تواند قطعی بسازد؛ شمارندهٔ
`networkFailures` جدا از `internalErrors` است.

## ۴. سناریو ۲ — خطای داخلی موتور (تفکیک از قطعی)

آزمون: `engine-errors.test.mjs` (۸ تست).

| سناریو | نتیجه |
| --- | --- |
| `probe` استثنا پرتاب کند | `null` برمی‌گردد؛ صفر نمونه، صفر قطعی، `total_checks` بدون تغییر، `internalErrors = 1`، کد خطا حفظ می‌شود، هشدار مستقل `kind='engine'` با `device_id = NULL` |
| `probe` هرگز برنگردد | مهلت سخت (پیش‌فرض: `attempts × (timeout×count + 2500) + 2000`ms) بررسی را می‌بندد؛ آزمون با مهلت ۶۰ms **در ۶۴ms** تمام شد و `inflight` خالی شد |
| چهار پروب آویزان با `max_workers = 2` | هر چهار بررسی با مهلت ۵۰ms بسته شدند؛ `inflight = 0` و **صفر نمونهٔ ناقص** |
| درج نمونه با Trigger شکست بخورد | کل تراکنش برمی‌گردد: وضعیت، `total_checks` و `last_check_at` بدون تغییر؛ کد خطا `ENGINE_DB`؛ بررسی بعدی سالم ثبت می‌شود |
| حالت واقعی (`tcp`) روی پورت بستهٔ محلی | نتیجه `mode='tcp'` است و **هرگز** `simulate` نمی‌شود؛ نمونهٔ ثبت‌شده هم `mode='tcp'` دارد |
| اختلال موتور (حلقه ۶۰ ثانیه عقب) | یک هشدار مستقل `kind='engine'`؛ تکرار فوری هشدار تازه نمی‌سازد؛ پس از دورهٔ بی‌خطایی (`incidentGraceMs`) بسته می‌شود |

خطاها به‌صورت ساختاریافته با کد (`ENGINE_DB`, `ENGINE_PROBE`, `ENGINE_STALLED`,
`ENGINE_LAG`, یا کد صریح لایهٔ پروب) در `engine_log` و لاگ JSON ثبت می‌شوند.

## ۵. سناریو ۳ — Restart و Recovery

آزمون: `engine-scheduling.test.mjs`.

| سناریو | نتیجه |
| --- | --- |
| Stop موتور | وضعیت تجهیزات (online/offline) تغییر نمی‌کند؛ صفر نمونه ثبت می‌شود |
| نمونهٔ آماده‌به‌کار | `checksRun = 0`؛ هیچ تجهیزی Offline نمی‌شود |
| Start با قطعیهٔ یتیم (ارجاع گم‌شده) | قطعی باز **بسته نمی‌شود**؛ `current_outage_id` و `current_outage_started_at` اصلی بازگردانده می‌شود؛ تجهیز همچنان Offline |
| `restart()` | رهبری دوباره گرفته می‌شود؛ نه قطعی بسته می‌شود نه تکراری ساخته می‌شود |
| ارجاع به قطعیهٔ بسته | در `recoverState` پاک می‌شود (`dangling = 1`) و وضعیت تجهیز دست‌نخورده می‌ماند |
| اندازه‌گیری مستقیم (۲۰۰ تجهیز) | `start` → رهبری در **۱۰۵ms**؛ `restart` (بدون بررسی در جریان) در **۲۴ms**؛ `internalErrors = 0`؛ `healthy = true` |

## ۶. سناریو ۴ — Crash ناگهانی و قفل Lease

آزمون: `engine-crash.test.mjs` (بین‌فرآیندی، `SIGKILL`).

| گام | نتیجه |
| --- | --- |
| `kill -9` وسط تراکنش چندمرحله‌ای موتور (درج قطعی + تغییر وضعیت تجهیز) | `PRAGMA quick_check = ok`؛ **صفر** قطعی باقی می‌ماند؛ هیچ تجهیزی Offline نشده؛ تعداد تجهیزات سالم (۳)؛ جدول `engine_lock` خالی |
| اجرای `engine-cli --once` **پیش از انقضای Lease** | بررسی انجام نمی‌شود (`samples = 0`) — دو موتور هم‌زمان Ping نمی‌زنند |
| انقضای Lease دارندهٔ کشته‌شده | Lease خودش منقضی می‌شود (در آزمون با TTL=۷۰۰ms) |
| اجرای بعدی پس از انقضا | رهبر می‌شود، هر ۳ تجهیز را **دقیقاً یک بار** بررسی می‌کند، قفل در خروج آزاد می‌شود و هیچ تجهیزی بیش از یک قطعی باز ندارد |

آزمون `two concurrent engines check every device exactly once` (قبلی، سبز): دو
فرآیند `engine-cli --once` هم‌زمان ⇒ `samples = devices` (بدون نمونهٔ تکراری) و
`engine_lock` خالی در پایان.

## ۷. سناریو ۵ — بار بالا و صف محدود

اندازه‌گیری با `npm run load -- --devices 1000 --workers 128 --probe-latency 3`:

| شاخص | مقدار اندازه‌گیری‌شده |
| --- | --- |
| یک چرخهٔ کامل ۱۰۰۰ تجهیز | **۲٬۹۲۲ms** (۳۴۲٫۲ بررسی/ثانیه) |
| اوج هم‌زمانی واقعی | **۱۲۸** — برابر `max_workers`، هرگز بیشتر (سقف رعایت شد) |
| خطای موتور | **۰** |
| CPU | ۱٬۱۳۵ms (≈۱٫۱۴ms به‌ازای هر بررسی) |
| حافظه | ۹۲٫۸ → ۱۰۰٫۶ مگابایت |
| تأخیر حلقهٔ رویداد | میانگین ۳۱٫۸ms، p99 ۵۵٫۶ms، بیشینه ۶۵۱ms |
| صف بررسی | ورودی هر چرخه `min(capacity×2, 500)`؛ تجهیزات معوق در جدول `devices` می‌مانند (نه در صف حافظه‌ای) و شاخص `backlog` آن‌ها را گزارش می‌کند |

آزمون واحد `high load is drained in bounded batches without an unbounded queue`:
۶۰ تجهیز سررسیدشده با `max_workers = 4` ⇒ همه در دسته‌های ۴تایی بررسی شدند،
**هر تجهیز دقیقاً یک نمونه**، `internalErrors = 0`، و اوج هم‌زمانی هرگز از ۴ رد نشد.

شاخص Scheduling Lag در همان اندازه‌گیری ۲۰۰تجهیزه (۳۲ worker، بازهٔ ۵ ثانیه):
`lastLag = ۷٬۰۲۳ms`، `avgLag = ۷٬۹۳۷ms`، `maxLag = ۸٬۴۹۴ms` — یعنی موتور دقیقاً
همان عقب‌ماندگی را که قرار است دیده شود، قابل‌اندازه‌گیری کرد (و آستانهٔ هشدار
`2× بازه` را رد کرد).

## ۸. بار زیاد و «ثبت دوبارهٔ نمونه در یک چرخه»

| آزمون | نتیجه |
| --- | --- |
| `one engine cycle records exactly one sample per device` | ۳ تجهیز سررسیدشده، ۱۰ چرخهٔ پیاپی ⇒ هر تجهیز **۱ نمونه**؛ چرخهٔ بعدی پیش از سررسید نمونهٔ تازه نمی‌سازد |
| `overlapping ticks never exceed max_workers` | سه `tick` هم‌زمان با `max_workers = 2` ⇒ اوج ۲ |
| `scheduled and actual start times...` | `samples.scheduled_at` = سررسید، `samples.started_at` = شروع واقعی، `scheduling.samples = 1` |
| `a manual check does not pollute the scheduling lag metric` | بررسی دستی در شاخص زمان‌بندی شمرده نمی‌شود (اما زمان‌هایش ثبت می‌شود) |

مکانیزم: پیش از اجرای پروب، سررسید همان تجهیز در همان تراکنش جلو برده می‌شود و
بررسی‌های در جریان بر پایهٔ شناسهٔ تجهیز یکتا می‌شوند؛ پس نه دو `tick` هم‌زمان و نه
یک بررسی دستی همراه موتور، نمونهٔ دوم نمی‌سازند.

## ۹. دادهٔ شبیه‌سازی در برابر دادهٔ واقعی

- پیش‌فرض عملیاتی `auto` است (پایش واقعی). برای دمو/آموزش باید صریحاً
  `simulate` انتخاب شود (`NETWATCH_ENGINE_MODE=simulate` یا تنظیمات ← موتور).
- هر نمونه ستون `mode` دارد و «نمونه‌های اخیر» هر تجهیز همین را نمایش می‌دهد.
- `engine_mode === 'simulate'` در `/api/engine/status` و `/api/system/health`
  به‌صورت فیلد `simulation` و در `engine_log`/لاگ JSON به‌صورت رویداد
  `engine_simulation_enabled` دیده می‌شود.
- خروج از حالت شبیه‌سازی، حالت داخلی شبیه‌ساز را پاک می‌کند تا بازگشت دوبارهٔ
  حالت، ادامهٔ «قطعی‌های ساختگی» قبلی نباشد.
- در حالت‌های واقعی هیچ مسیری به `simulateCheck` نمی‌رسد (آزمون‌شده).

## ۱۰. محدودیت‌های باقی‌مانده

- **قفل رهبری تک‌گرهی است.** روی یک پایگاه‌دادهٔ SQLite (حتی در حالت WAL) قفل
  درست کار می‌کند؛ برای چندسروری واقعی به قفل توزیع‌شده (مثلاً Lease در
  PostgreSQL/Redis) نیاز است.
- **پنجرهٔ هم‌پوشانی نظری:** اگر رهبر واقعاً زنده باشد ولی بیش از TTL پاسخ ندهد
  (توقف طولانی فرآیند/زمان‌بند OS)، نمونهٔ دوم می‌تواند پیش از مرگ او رهبر شود.
  TTL پیش‌فرض ۱۵ ثانیه است و با `NETWATCH_ENGINE_LOCK_TTL_MS` قابل تنظیم است؛
  انتخاب TTL کوتاه‌تر = تشخیص سریع‌تر Crash، TTL بلندتر = احتمال کمتر هم‌پوشانی.
- **مهلت سخت یک تور ایمنی است، نه جایگزین `timeout_ms`.** مقدار پیش‌فرض بر پایهٔ
  `timeout_ms × packet_count × attempts` محاسبه می‌شود؛ اگر آن را دستی روی
  عددی کوچک بگذارید، پروب‌های سالمِ کند هم بسته می‌شوند.
- **دسترس‌پذیری ICMP/TCP شرط پایش واقعی است.** در محیطی که نه مجوز RAW socket
  هست و نه پورت TCP قابل اتصال، بررسی‌ها واقعاً «ناموفق» هستند؛ موتور در آن
  حالت دادهٔ ساختگی نمی‌سازد (به‌عمد) و تجهیزات Offline می‌شوند.
- **هشدار موتور در همان جدول `alerts` با `kind='engine'` و `device_id = NULL`
  است.** رابط کاربری آن را در مرکز هشدارها نشان می‌دهد؛ صفحهٔ اختصاصی «رخدادهای
  موتور» هنوز ساخته نشده (لاگ و شاخص‌ها در `/api/engine/status` موجود است).
- **دادهٔ نمایشی در نخستین اجرا ساخته می‌شود** (وقتی پایگاه‌داده خالی است).
  حالت موتور را روشن نمی‌کند، اما اگر سامانه را برای پایش واقعی نصب می‌کنید،
  تجهیزات نمونه را از فهرست حذف کنید یا پایگاه‌داده را با دادهٔ خودتان
  راه‌اندازی کنید (`npm run seed:reset` داده‌های نمایشی را بازمی‌سازد).
