# گزارش بهینه‌سازی پرس‌وجو و عملکرد پایگاه‌داده

**NetWatch — فاز ۲** · تاریخ: ۲۰۲۶‑۱۰‑۱۹
دادهٔ خام اندازه‌گیری‌ها: [phase2-scale-measurements.json](phase2-scale-measurements.json)
ابزار بازتولید: `npm run db:scale` و `npm run db:doctor`

## ۱. خلاصهٔ اجرایی

| معیار | نتیجه در مقیاس سنجش (۳٬۰۰۰٬۰۰۰ نمونه / ۲۰۰ تجهیز / ۱۲۰ روز) |
| --- | --- |
| درج کل داده | ۳٬۰۰۰٬۰۰۰ نمونه در **۱۰۷ ثانیه** (≈ ۲۸٬۰۰۰ ردیف/ثانیه، Batch ۵۰٬۰۰۰) |
| حجم پایگاه‌داده | ۴۳۹MB (با ایندکس‌ها) — ۱۸۸MB پس از هرس ۵۰٪ دادهٔ قدیمی |
| Query داغ نمودار (۱ ساعت) | **۰٫۰۲ms** |
| Query گزارش (۲۴ ساعت، bucketed) | **۰٫۲۴ms** |
| شمارش دسترس‌پذیری یک تجهیز | **۱٫۲ms** |
| تجهیزات سررسیدشده | **۰٫۲۵ms** |
| تجمیع روزانه در بازهٔ ۱ روزه برای همهٔ تجهیزات | **۱۸۵ms** (اسکن پوششی ایندکس) |
| WAL پس از تودهٔ نوشتن | ۱۶MB → پس از Checkpoint **صفر**؛ Checkpoint **۲٫۷ms** |
| Retention (حذف ۱٫۵ میلیون ردیف) | **۴۳٫۷ ثانیه** با ۸۱ تراکنش مستقل (Batch ۲۰٬۰۰۰) |
| پشتیبان‌گیری (عکس لحظه‌ای ۱۸۸MB) | **۱۶٫۲ ثانیه**؛ اعتبارسنجی **۱۴٫۰ ثانیه** |
| `integrity_check` کامل روی ۴۴۰MB | **۱۶٫۶ ثانیه**، نقض کلید خارجی **صفر** |
| اوج حافظهٔ فرآیند | ۱۵۸MB RSS · ۶۰MB Heap |
| CPU (۳ دقیقه و ۲۲ ثانیه کار) | User ۷۱s · System ۱۲۳s (روی ۲ هسته) |
| Disk I/O | نوشتن ۳٫۳۷GB (شامل WAL/Checkpoint/پشتیبان) |

**نتیجه:** پرس‌وجوهای حیاتی داشبورد در مقیاس میلیونی زیر ۲ میلی‌ثانیه پاسخ می‌دهند؛
تنها پرس‌وجوی تجمیعی «یک روز کامل برای همهٔ تجهیزات» ماهیتاً اسکن ایندکس است و با
کش/بازهٔ مناسب اجرا می‌شود.

## ۲. پرس‌وجوهای داغ و پلن واقعی

خروجی `EXPLAIN QUERY PLAN` (همه روی پایگاه‌دادهٔ ۳ میلیون نمونه):

| پرس‌وجو | پلن | زمان (میانگین) |
| --- | --- | --- |
| سری نمودار یک تجهیز، ۱ ساعت | `SEARCH samples USING INDEX idx_samples_device_ts (device_id=? AND ts>?)` | ۰٫۰۲ms |
| گزارش ۲۴ ساعت با Bucketing | همان ایندکس | ۰٫۲۴ms |
| `COUNT(*) … device_id=? AND ok=1` | `SEARCH … USING COVERING INDEX idx_samples_device_ok` | ۱٫۲ms |
| تجهیزات سررسیدشده | `SEARCH devices USING INDEX idx_devices_due` | ۰٫۲۵ms |
| قطعی‌های یک تجهیز | `SEARCH outages USING INDEX idx_outages_device` | ۰٫۲۶ms |
| هشدارهای فعال | `SEARCH alerts USING INDEX idx_alerts_status` | ۰٫۰۲ms |
| آمار روزانهٔ بلندمدت | `SEARCH daily_stats USING INDEX idx_daily_day` | ۳۴ms (۲۶٬۰۰۰ ردیف) |
| فهرست حسابرسی | `SCAN audit_log USING INDEX idx_audit_ts` (اسکن ایندکس) | ۰٫۰۱ms |
| تجمیع ۲۴ ساعته همهٔ تجهیزات | `SCAN samples USING COVERING INDEX idx_samples_device_ts` | ۱۸۵ms |

**قاعدهٔ پذیرش خودکار:** `db-query-plan.test.mjs` تضمین می‌کند هیچ پرس‌وجوی داغی
روی جدول بزرگ «SCAN جدول بدون ایندکس» نداشته باشد؛ `npm run db:doctor` با کد خروج
۱ هر رگرسیون را گزارش می‌کند.

### پرس‌وجوهای Retention (فاز ۲)

| پرس‌وجو | پلن |
| --- | --- |
| شمارش نمونه‌های قابل‌حذف | `SEARCH samples USING INDEX idx_samples_ts` |
| شمارش قطعی‌های قابل‌حذف | `SEARCH o USING INDEX idx_outages_closed_started` + `SEARCH m/d USING COVERING INDEX` |
| شمارش هشدارهای قابل‌حذف | `SEARCH a USING INDEX idx_alerts_status` + `SEARCH o USING INDEX idx_outages_open` |
| حذف Batchی نمونه | `SEARCH samples USING INDEX idx_samples_ts` + حذف با rowid |
| حذف Batchی آمار روزانه | `SEARCH daily_stats USING INDEX idx_daily_day` |
| حذف Batchی حسابرسی | `SCAN audit_log USING INDEX idx_audit_ts` (اسکن ایندکس، نه جدول) |

## ۳. بازبینی ایندکس‌ها

- **افزوده‌شده در فاز ۲:** `idx_devices_layer`، `idx_alerts_rule`،
  `idx_alert_rules_group` (ایندکس کلیدهای خارجی که SQLite خودکار نمی‌سازد) و
  `idx_outages_ended` (بازه‌های مبتنی بر پایان قطعی).
- **غیرضروری:** هیچ ایندکسی حذف نشد؛ در بازبینی همهٔ ۳۹ ایندکس به پرس‌وجویی
  نگاشت می‌شوند. دو مورد هم‌پوشان جزئی (`idx_outages_started` سراسری و
  `idx_outages_closed_started` جزئی) عمداً حفظ شدند چون اولی ترتیب زمانی سراسری و
  دومی هرس قطعی‌های بسته را پوشش می‌دهد.
- **مفقود:** با بررسی پلن‌ها و ایندکس‌های FK، تنها شکاف‌ها همان سه ایندکس FK فوق
  بودند که اضافه شدند.
- **هزینهٔ ایندکس:** درج ۳ میلیون ردیف با ۴ ایندکس روی `samples` انجام می‌شود؛
  هزینهٔ نگهداری در نرخ ۲۸٬۰۰۰ ردیف/ثانیه دیده می‌شود که برای بار واقعی
  (۱ تجهیز × هر ۳۰ ثانیه = ۳٬۰۰۰ ردیف در روز برای ۱۰۰۰ تجهیز) بسیار پایین است.

## ۴. WAL، Checkpoint و دوام

| مشاهده | مقدار |
| --- | --- |
| WAL پس از ۳ میلیون درج | ۱۶٫۴MB |
| `wal_autocheckpoint` | ۱۰۰۰ صفحه (≈۴MB) → Checkpoint خودکار در میانهٔ کار |
| Checkpoint دستی `TRUNCATE` | ۲٫۷ms، `busy=0` |
| WAL پس از Checkpoint | صفر (فایل خالی می‌ماند) |
| `journal_size_limit` | ۶۴MB (سقف رشد WAL) |
| `synchronous` | `FULL` — همهٔ سنجش‌ها با همین سیاست دوام انجام شده‌اند |

با `synchronous=FULL` هر Commit به دیسک می‌رود؛ به همین دلیل نرخ درج Batchی است و
نه مبتنی بر حافظه. برای نصب‌های پرنوشت، `NETWATCH_SQLITE_SYNC=NORMAL` کاهش آگاهانهٔ
دوام است و در سیاست پیش‌فرض توصیه نمی‌شود.

## ۵. تراکنش‌های طولانی

- بزرگ‌ترین تراکنش قابل‌انتظار، **Batch هرس** است: با `retention_batch_size=20000`
  اندازه‌گیری واقعی ≈ **۵۴۰ms** برای هر Batch (۱٫۵ میلیون ردیف در ۸۱ تراکنش و
  ۴۳٫۷ ثانیه). هیچ تراکنشی در مسیر موتور از این طول فراتر نمی‌رود.
- درج نتایج موتور در تراکنش‌های تک‌عملیاتی انجام می‌شود؛ زمان هر تراکنش تحت بار
  واقعی در حد چند میلی‌ثانیه است.
- ورود گروهی Excel/CSV و عملیات گروهی نیز در یک تراکنش با سقف ۵۰٬۰۰۰ ردیف
  (قابل تنظیم با `NETWATCH_MAX_IMPORT_ROWS`) اجرا می‌شوند؛ برای فایل‌های بزرگ،
  پردازش در Worker Thread و با محدودیت هم‌زمانی انجام می‌شود.
- `PRAGMA optimize` در هر راه‌اندازی و پس از هر اجرای Retention اجرا می‌شود تا
  آمار بهینه‌ساز تازه بماند.

## ۶. Import هم‌زمان با Probe

دو فرآیند مستقل روی همان پایگاه‌داده (سرور/engine-cli واقعی) هم‌زمان نوشتند:

| فرآیند | عملیات | نتیجه |
| --- | --- | --- |
| Import (فرآیند فرزند) | درج ۸۰۰ تجهیز با IP یکتا | **۸۰۰ موفق، ۰ خطا** |
| Probe (فرآیند فرزند) | درج ۱٬۵۰۰ نمونه با timestamp یکتا | **۱٬۵۰۰ موفق، ۰ خطا** |
| بررسی پس از اجرا | شمارش ردیف‌ها + health | تطبیق کامل، `integrity ok`، نقض FK صفر |
| خطای BUSY | شمارش رویدادهای قفل | **صفر** (`busy_timeout=5000` + تلاش دوباره) |

| منبع | مقدار |
| --- | --- |
| CPU (user/system) | ۷۱s / ۱۲۳s روی ۲ هسته |
| اوج RSS | ۱۵۸MB |

## ۸. یافته‌ها و توصیه‌ها

1. **`integrity_check` کامل روی پایگاه‌دادهٔ ۴۴۰MB حدود ۱۶٫۶ ثانیه طول می‌کشد.**
   به همین دلیل بررسی راه‌اندازی به‌صورت پیش‌فرض `quick_check` است و بررسی کامل
   فقط با `NETWATCH_DB_CHECK=full`، از `db:doctor` یا پیش از بازیابی اجرا می‌شود.
2. **پرس‌وجوی تجمیع ۲۴ ساعته برای همهٔ تجهیزات** (۱۸۵ms در ۱٫۵ میلیون ردیف) را
   نباید در هر درخواست داشبورد تکرار کرد؛ مسیرهای گزارش از بازه‌های Bucket دار و
   `daily_stats` استفاده می‌کنند.
3. **هرس با Batch ۲۰٬۰۰۰ حدود ۰٫۵ ثانیه** حلقهٔ رویداد را در هر گام نگه می‌دارد؛
   برای نصب‌های بسیار پرنوشت می‌توان `retention_batch_size` را به ۵٬۰۰۰ کاهش داد
   (پیش‌فرض) تا هر گام کوتاه‌تر شود.
4. **Backup/Restore همگام هستند.** برای پایگاه‌داده‌های چند گیگابایتی، اجرای آن‌ها
   از سرویس خارج از ساعت کاری توصیه می‌شود (در مقیاس ۱۸۸MB: ۱۶ ثانیه).
5. **ایندکس‌های `samples` سقف عملی دارند:** با نگهداری ۹۰ روز نمونهٔ خام و
   ۱۰۰۰ تجهیز با بازهٔ ۳۰ ثانیه، حجم نمونه ≈ ۲۵۰ میلیون ردیف در ۹۰ روز است که
   فراتر از دامنهٔ سنجش فعلی است؛ برای چنین مقیاسی باید بازهٔ نمونهٔ خام کوتاه‌تر
   (مثلاً ۳۰ روز) یا نمونه‌برداری تجمیعی در نظر گرفته شود (ریسک باقی‌مانده در
   [phase2-remaining-risks.md](phase2-remaining-risks.md)).
