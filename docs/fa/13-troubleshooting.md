# بازیابی پس از خرابی و عیب‌یابی

این سند بر اساس **نشانه** تنظیم شده است: ابتدا نشانه را پیدا کنید، سپس علت و
اقدام. هدف این است که در شرایط خرابی، مسیر بعدی روشن باشد — نه فهرست طولانی
حدس‌ها.

> پیش از هر اقدام، دو چیز را بگیرید: `sudo journalctl -u netwatch -n 200 --no-pager`
> و `npm run db:doctor`. لاگ‌ها ساختاریافته (JSON) هستند و فیلد `event` بهترین
> نقطهٔ شروع است.

---

## ۱. سرویس بالا نمی‌آید

| نشانه | علت احتمالی | اقدام |
| --- | --- | --- |
| `پیکربندی نامعتبر است` | `PORT`/`HOST`/CIDR/TLS/نرخ نامعتبر | پیام دقیق را بخوانید؛ فقط نام کلید و بازهٔ مجاز چاپ می‌شود |
| `EADDRINUSE` | پورت اشغال (نمونهٔ قدیمی زنده است) | `ss -ltnp \| grep 8787` و توقف سرویس قبلی |
| `EACCES` / `EPERM` | مالکیت داده/کلید اشتباه | `chown -R netwatch:netwatch /var/lib/netwatch` |
| `پایگاه‌داده آسیب دیده است` (`DB_CORRUPT`) | خرابی فایل/WAL | بازگشت به پشتیبان معتبر (بخش ۳) |
| `مهاجرت ساختار داده ... ناموفق` | تعارض ساختار یا کمبود فضا | لاگ `db_migration_applied` و پیام گام (بخش ۴) |
| خطای TLS | گواهی/کلید ناقص یا ناخوانا | مسیر و مجوز `server.key` (`600`) |

اگر عمداً می‌خواهید روی پایگاه‌دادهٔ ناسالم سرویس را **برای بازیابی** بالا
بیاورید، فقط به‌طور موقت:

```bash
NETWATCH_DB_CHECK=warn
```

> ⚠️ `off` یا `warn` را دائمی نکنید؛ خرابی پایگاه‌داده باید دیده شود، نه نادیده.

---

## ۲. ورود ناموفق است

| نشانه | علت | اقدام |
| --- | --- | --- |
| «نام کاربری یا رمز نادرست» با رمز درست | حساب قفل شده | `POST /api/auth/users/<id>/unlock` با Admin |
| `429` + `Retry-After` | سقف نرخ ورود | صبر؛ بازبینی `NETWATCH_LOGIN_RATE_LIMIT_MAX` |
| بلافاصله پس از ورود خارج می‌شود | کوکی `Secure` روی HTTP | از HTTPS استفاده کنید یا پروکسی را درست تنظیم کنید |
| `403` روی APIهای مدیریتی | محدودیت شبکهٔ مدیریت | `NETWATCH_ADMIN_ALLOWED_CIDRS` و IP واقعی (`NETWATCH_TRUST_PROXY`) |
| `CSRF` نامعتبر | هدر `X-CSRF-Token` جا افتاده | توکن کوکی `nw_csrf` را بفرستید |
| `401` برای همهٔ APIها | نشست منقضی/باطل | ورود دوباره (Idle Timeout پیش‌فرض ۶۰ دقیقه) |

قفل حساب در پایگاه‌داده ذخیره می‌شود؛ ری‌استارت سرور آن را باز نمی‌کند.

## ۳. خرابی پایگاه‌داده

نشانه‌ها: `DB_CORRUPT`، `database disk image is malformed`، `quick_check` ناموفق،
یا `db:doctor` با خطا.

```bash
sudo systemctl stop netwatch
sudo -u netwatch env NETWATCH_DATA_DIR=/var/lib/netwatch npm run db:doctor -- --json

# آخرین پشتیبان‌ها
ls -1t /var/lib/netwatch/backups | head -5

# اعتبارسنجی بدون تغییر
sudo -u netwatch env NETWATCH_DATA_DIR=/var/lib/netwatch \
  npm run db:restore -- /var/lib/netwatch/backups/<backup> --dry-run --no-mbtiles

# بازیابی و راه‌اندازی
sudo -u netwatch env NETWATCH_DATA_DIR=/var/lib/netwatch \
  npm run db:restore -- /var/lib/netwatch/backups/<backup> --no-mbtiles
sudo systemctl start netwatch
```

اگر پشتیبان ندارید:

1. سرویس را با `NETWATCH_DB_CHECK=warn` موقتاً بالا بیاورید و داده‌های قابل‌خواندن
   را استخراج کنید (گزارش‌ها، خروجی Excel).
2. از فایل خراب یک کپی نگه دارید (برای بازیابی تخصصی).
3. پایگاه‌دادهٔ تازه بسازید و داده‌ها را از Import بازگردانید.

جزئیات کامل در [پشتیبان‌گیری و بازیابی](11-backup-restore.md).

## ۴. خطای Migration در ارتقا

```bash
sudo journalctl -u netwatch | grep -E "db_migration|MIGRATION_FAILED|Migration"
```

| گام | کار |
| --- | --- |
| ۱ | علت را رفع کنید: فضای دیسک، تعارض نام شیء، مجوز فایل |
| ۲ | دوباره راه‌اندازی کنید؛ Migration از آخرین گام موفق ادامه می‌یابد |
| ۳ | اگر رفع ممکن نیست: فایل `netwatch.db.pre-migration-v<old>-<ts>` را جایگزین و کد نسخهٔ قبلی را نصب کنید |

گام شکست‌خورده Rollback شده است؛ نیازی به پاک‌کردن دستی جدول‌ها نیست. رویهٔ کامل
در [ارتقا و انتشار](15-upgrade-release.md).

## ۵. موتور بررسی نمی‌کند

| نشانه | بررسی | اقدام |
| --- | --- | --- |
| `running=false` | `GET /api/engine/status` | `POST /api/engine/control/start` |
| `leader=false` و نمونهٔ دیگر رهبر است | `epoch`, `lock.owner` | طبیعی است؛ فقط یک رهبر مجاز است |
| `mode=tcp` به‌جای `icmp` | `icmpAvailable` | نصب `iputils-ping` و اعطای `CAP_NET_RAW` |
| `stalled=true` / `tickLagMs` بزرگ | backlog و تعداد تجهیزات | تنظیم `max_workers` یا `ping_interval` |
| backlog صعودی | `max_workers × interval < devices` | افزایش ظرفیت یا کاهش تعداد تجهیزات فعال |
| همهٔ تجهیزات `offline` | فایروال/مسیر/`probe_allowed_cidrs` | از خود سرور `ping`/`nc` بزنید؛ محدودهٔ Probe را بررسی کنید |
| `ENGINE_NOT_LEADER` در بررسی دستی | این نمونه رهبر نیست | بررسی را از نمونهٔ رهبر اجرا کنید |

```bash
# آیا ICMP از خود سرور کار می‌کند؟
ping -c 3 10.0.0.2

# آیا پورت TCP باز است؟
nc -zv 10.0.0.2 80
```

## ۶. داده زنده در رابط کاربری به‌روز نمی‌شود

| نشانه | علت | اقدام |
| --- | --- | --- |
| «اتصال قطع است» و «داده کهنه» | SSE قطع شده | شبکه/پروکسی؛ `proxy_buffering off` در Nginx |
| «در حال اتصال…» پایدار | `/api/events` مسدود است | فایروال/پروکسی و `NETWATCH_SSE_MAX` را بررسی کنید |
| کلاینت‌ها مرتب قطع می‌شوند | بافر/شبکهٔ کند | `NETWATCH_SSE_MAX_BUFFER`؛ لاگ `sse_client_dropped` |
| داشبورد قدیمی ولی تجهیزات تازه | کش مرورگر | Hard Reload؛ APIها `no-store` هستند |

SSE پس از قطع با Backoff نمایی + Jitter دوباره وصل می‌شود و پس از اتصال،
Snapshotها را دوباره می‌گیرد تا دادهٔ قدیمی «زنده» نمایش داده نشود.

## ۷. ورود گروهی (Import) کار نمی‌کند

| نشانه | علت | اقدام |
| --- | --- | --- |
| `413` | حجم فایل بیش از سقف | `NETWATCH_MAX_IMPORT_BYTES` (پیش‌فرض ۱۰MiB) |
| `400` با فهرست خطا | ستون/مقدار نامعتبر | فایل نمونه (`/api/devices/template`) را بگیرید |
| `429` | سقف نرخ Import | `NETWATCH_IMPORT_RATE_LIMIT_MAX` |
| `503` | صف پردازش پر است | `NETWATCH_JOB_CONCURRENCY` یا تلاش دوباره |
| ردیف تکراری ثبت نمی‌شود | IP تکراری | پیش‌نمایش دلایل را نشان می‌دهد |
| متن فارسی خراب | نبود BOM/UTF-8 | فایل را با UTF-8 و BOM ذخیره کنید |

## ۸. پشتیبان‌گیری یا بازیابی ناموفق

| نشانه | علت | اقدام |
| --- | --- | --- |
| «فضای دیسک کافی نیست» | نیاز `VACUUM INTO` بیشتر از فضای آزاد | آزادسازی فضا؛ `NETWATCH_MIN_FREE_BYTES` |
| «پشتیبان ساخته‌شده معتبر نیست» | فایل ناقص/خراب | دیسک را بررسی کنید؛ پشتیبان قبلی را نگه دارید |
| `409` | پشتیبان‌گیری/بازیابی هم‌زمان | چند لحظه صبر و تلاش دوباره |
| «بازیابی ... مجاز نیست» | نسخهٔ پشتیبان جدیدتر از برنامه | برنامه را ارتقا دهید |
| `db:restore` امتناع می‌کند | سرویس در حال اجراست | `systemctl stop netwatch` |

## ۹. Retention متوقف می‌شود

| نشانه | علت | اقدام |
| --- | --- | --- |
| `blocked.samples = missing_daily_stats:N` | روز تجمیع‌نشده در بازهٔ حذف | عادی است؛ اجرای بعدی ادامه می‌دهد |
| `status: skipped` با `reason: legal_hold` | Legal Hold فعال | اگر الزام قانونی نیست، خاموش کنید |
| `409` | اجرای هم‌زمان/قفل نمونهٔ دیگر | `--status` را ببینید؛ قفل پس از انقضا آزاد می‌شود |
| `status: interrupted` | Crash در اجرای قبلی | اجرای دستی بعدی آن را علامت می‌زند |
| رشد دیسک با وجود Retention | بازهٔ بزرگ یا سقف `max_rows_per_run` | سیاست و سقف را تنظیم کنید |

## ۱۰. خطاهای پرتکرار API

| کد | معنی | اقدام |
| --- | --- | --- |
| `400` | ورودی نامعتبر | بدنه/پارامتر را با [API](06-api.md) تطبیق دهید |
| `401` | بدون نشست معتبر | ورود دوباره |
| `403` | نبود مجوز یا شبکهٔ غیرمجاز | نقش کاربر و `NETWATCH_ADMIN_ALLOWED_CIDRS` |
| `404` | منبع یافت نشد | شناسه را بررسی کنید |
| `409` | تعارض وضعیت (قفل/بازیابی/نسخهٔ رهبری) | چند لحظه بعد تلاش کنید |
| `413` | حجم بیش از حد | سقف‌های Import/MBTiles |
| `429` | سقف نرخ | `Retry-After` را رعایت کنید |
| `503` | صف پر/سرویس در حال بازیابی | بعداً تلاش کنید |
| `504` | مهلت سخت Probe تمام شد | تجهیز/شبکه را بررسی و در صورت نیاز `NETWATCH_PROBE_TIMEOUT_MS` را تنظیم کنید |

### خطاهای اختصاصی Probe

| نشانه | معنا | اقدام |
| --- | --- | --- |
| `429` روی `/ping` یا `/bulk` | سهمیهٔ Probe (`NETWATCH_PROBE_RATE_LIMIT_MAX`) | صبر به اندازهٔ `Retry-After`؛ به‌جای درخواست تکراری، نتیجهٔ Job را بخوانید |
| `503` با کد `PROBE_QUEUE_FULL` | صف مرکزی پر است | چند ثانیه صبر یا افزایش `NETWATCH_PROBE_QUEUE_MAX`/`NETWATCH_PROBE_CONCURRENCY` |
| `504` با کد `PROBE_TIMEOUT` | کار از مهلت سخت گذشت و Abort شد | بررسی مقصد؛ در صورت نیاز افزایش `NETWATCH_PROBE_TIMEOUT_MS` |
| `202` از `POST /devices/bulk` | Job ساخته شد، نتیجه هنوز آماده نیست | `statusUrl` را تا `done` دنبال کنید |

## ۱۱. جدول کدهای خطای پایگاه‌داده

`server/db-errors.js` خطاهای SQLite را دسته‌بندی می‌کند:

| کد | معنی | اقدام معمول |
| --- | --- | --- |
| `DB_BUSY` | قفل پایگاه‌داده | تلاش دوباره؛ `NETWATCH_BUSY_TIMEOUT_MS` |
| `DB_DISK_FULL` | دیسک پر | آزادسازی فضا؛ Retention |
| `DB_CORRUPT` | فایل خراب | بازیابی از پشتیبان |
| `DB_CONSTRAINT` | نقض قید (یکتایی/خارجی) | دادهٔ ورودی را اصلاح کنید |
| `DB_BINDING` | نوع مقدار نامعتبر در پرس‌وجو | باگ/ورودی غیرمنتظره؛ لاگ شامل SQL است |
| `DB_READONLY` | فایل فقط‌خواندنی | مجوز/مالکیت پوشهٔ داده |
| `DB_IO` | خطای I/O | سلامت دیسک را بررسی کنید |
| `DB_BACKUP_INVALID` | پشتیبان نامعتبر | پشتیبان دیگر را امتحان کنید |
| `DB_MIGRATION_FAILED` | شکست Migration | بخش ۴ |
| `DB_NOT_OPEN` | پایگاه‌داده بسته است | ری‌استارت سرویس |

## ۱۲. سناریوهای بازیابی سریع

| سناریو | اقدام کوتاه |
| --- | --- |
| Restart ناگهانی | `systemctl status`؛ در صورت خروج، `start`؛ WAL خودکار Replay می‌شود |
| SIGTERM | تخلیهٔ مرتب؛ کد خروج `0`؛ دادهٔ تأییدشده حفظ می‌شود |
| SIGKILL | پس از راه‌اندازی `db:doctor`؛ تراکنش نیمه‌کاره Rollback شده است |
| قطع شبکهٔ داخلی | دادهٔ محلی سالم است؛ موتور پس از بازگشت ادامه می‌دهد |
| از دست رفتن Lease رهبری | نمونهٔ دیگر رهبر می‌شود؛ نتایج دیررس با Fencing رد می‌شوند |
| فایل Import خراب | `400` با فهرست خطا؛ هیچ ردیفی ثبت نمی‌شود |
| توقف موتور در حین بررسی | بررسی‌های در جریان تخلیه/ابطال می‌شوند؛ رکورد نیمه‌کاره ساخته نمی‌شود |

## ۱۳. جمع‌آوری اطلاعات برای پشتیبانی

```bash
{
  date -Is; node -v; uname -a
  sudo systemctl status netwatch --no-pager | head -20
  curl -fsS http://127.0.0.1:8787/api/health
  sudo -u netwatch env NETWATCH_DATA_DIR=/var/lib/netwatch npm run db:doctor -- --json
  sudo journalctl -u netwatch -n 300 --no-pager
} > /tmp/netwatch-support.txt 2>&1
```

پیش از ارسال، مطمئن شوید فایل شامل رمز، توکن یا کلید خصوصی نیست. لاگ‌ها این
مقادیر را ثبت نمی‌کنند، اما خروجی دستی می‌تواند شامل آن‌ها باشد.
