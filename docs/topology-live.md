# وضعیت زندهٔ دیاگرام ارتباطات

این سند رفتار «نمای زنده» دیاگرام‌های توپولوژی را توضیح می‌دهد: رنگ و علت
وضعیت هر لینک از کجا می‌آید، از چه داده‌ای ساخته می‌شود، چگونه تازه می‌شود و
چه چیزهایی عمداً محاسبه نمی‌شود.

> پیاده‌سازی: `server/topology-live.js` (محاسبهٔ Snapshot) و
> `server/routes/topology.js` (مسیر `GET /diagrams/:id/status`).
> رابط کاربری: `web/src/lib/topology-live.ts` و صفحهٔ `Topology`.

---

## ۱. منبع داده

نمای زنده **هیچ پروب شبکه‌ای اجرا نمی‌کند**. تمام ورودی‌ها از داده‌ای می‌آید که
موتور پایش از قبل تولید کرده است:

```
devices (status, rtt, loss, thresholds)  ─┐
samples (۳۰ دقیقهٔ اخیر برای نوسان)       ├─▶ topology-live.js ─▶ Snapshot
topology_links.monitor_device_id          ─┘
```

- هر لینک می‌تواند **تجهیز مرجع سنجش** داشته باشد (`monitor_device_id`).
  اگر تنظیم نشده باشد، تجهیزات دو سر لینک به‌عنوان منبع استفاده می‌شوند.
- لینکی که هیچ تجهیز مرجعی ندارد و دو سرش هم به تجهیز متصل نیست، وضعیت
  `unknown` با علت `no-source` می‌گیرد. هیچ عددی حدس زده نمی‌شود.
- **ظرفیت اسمی** (`capacityMbps`) فقط مشخصه‌ای است که کاربر ثبت می‌کند و در
  تحلیل مسیرها و گزارش‌ها به کار می‌رود.

> **مصرف/اشغال ظرفیت محاسبه نمی‌شود.** خواندن شمارندهٔ اینترفیس (SNMP) از
> محصول حذف شده است؛ بنابراین فیلدهای `utilPct`، `rxMbps`، `txMbps`،
> `saturation`، `telemetryAt` و `operStatus` در پاسخ وجود ندارند. ظرفیت اسمی
> باقی می‌ماند، اما «درصد اشغال» فقط وقتی معنا داشت که شمارنده واقعی خوانده
> می‌شد و ادعای عددی بدون سنجش پذیرفته نیست.

## ۲. قواعد وضعیت

| رنگ | `status` | شرط |
| --- | --- | --- |
| سبز | `up` | همهٔ منابع تازه‌اند و افت/تأخیر/نوسان زیر آستانه است |
| زرد | `degraded` | یکی از منابع در وضعیت `warning` است یا افت/تأخیر/نوسان از آستانه گذشته |
| قرمز | `down` | دست‌کم یکی از تجهیزات دو سر (یا تجهیز مرجع) `offline` است |
| خاکستری | `unknown` | دادهٔ تازه یا کافی وجود ندارد |

کدهای علت (`reasonCode`) به ترتیب اولویت:

| کد | معنا |
| --- | --- |
| `no-source` | لینک هیچ منبع سنجش قابل‌استفاده‌ای ندارد |
| `stale` | دادهٔ منبع قدیمی‌تر از سقف مجاز است |
| `partial-stale` | بخشی از منابع تازه و بخشی قدیمی‌اند |
| `endpoint-offline` | تجهیز دو سر یا مرجع قطع است |
| `endpoint-unknown` | وضعیت تجهیز هنوز مشخص نیست |
| `endpoint-warning` | تجهیز در وضعیت هشدار (تأخیر/افت بالا) است |
| `loss` | درصد افت بسته از آستانهٔ مجاز گذشته است |
| `latency` | تأخیر از آستانهٔ مجاز گذشته است |
| `jitter` | نوسان تأخیر از آستانهٔ مجاز گذشته است |
| `healthy` | همه‌چیز در محدودهٔ سالم است |

آستانه‌های تأخیر و افت از تنظیمات سراسری موتور (`latency_threshold`،
`loss_threshold`) می‌آید. آستانهٔ نوسان ثابت `DEFAULT_JITTER_LIMIT_MS = 40ms`
است و از میانگین قدرمطلق اختلاف نمونه‌های متوالی (۵ تا ۱۰ نمونهٔ آخر در بازهٔ
۳۰ دقیقه) محاسبه می‌شود.

---

## ۳. تازگی داده

- سن داده از `last_check_at` تجهیز محاسبه می‌شود، نه از زمان درخواست.
- اگر داده قدیمی‌تر از سقف تازگی باشد، لینک `unknown`/`stale` می‌شود؛ رابط
  کاربری همان رنگ خاکستری را نشان می‌دهد و «وضعیت ناشناخته» را با عدد جعلی
  پر نمی‌کند.
- تجهیز در حالت تعمیرات (Maintenance) به‌عنوان منبع تازه شمرده نمی‌شود.

---

## ۴. تازه‌سازی و کش

- صفحهٔ دیاگرام هر **۱۰ ثانیه** وضعیت را از `/status` می‌خواند (تب مخفی:
  متوقف).
- در صورت اتصال SSE، رویدادهای واقعی شبکه حداکثر هر ۴ ثانیه یک بازخوانی
  زودتر را Trigger می‌کنند.
- بازگشت به تب، بازخوانی فوری با `?fresh=1` انجام می‌دهد.
- کش سمت سرور حداکثر ۳ ثانیه است (حداکثر ۶۴ دیاگرام)؛ N کاربر هم‌زمان باعث N
  بار محاسبه در هر ثانیه نمی‌شوند. با ذخیرهٔ دیاگرام یا تغییر وضعیت تجهیز، کش
  همان دیاگرام باطل می‌شود.
- وضعیت هرگز از سمت کلاینت قابل تغییر نیست؛ هیچ دکمهٔ «قطع/وصل» وجود ندارد.

---

## ۵. پیکربندی لینک

1. روی لینک کلیک کنید و در پنل بازرسی:
   - **پهنای باند اسمی** را وارد کنید (Mbps) یا یکی از گزینه‌های آماده را بزنید.
   - **تجهیز مرجع سنجش** را انتخاب کنید (اختیاری؛ پیش‌فرض تجهیزات دو سر لینک).
2. تغییرات با ذخیرهٔ دیاگرام اعمال می‌شود و کش وضعیت باطل می‌گردد.

برای اینکه لینک وضعیت معنادار داشته باشد، کافی است تجهیزات دو سر آن در سامانه
ثبت و پایش شده باشند؛ هیچ عامل بیرونی یا پورت خاصی لازم نیست.

## ۶. API

| مسیر | توضیح |
| --- | --- |
| `GET /api/topology/diagrams/:id/status` | Snapshot زندهٔ گره‌ها/لینک‌ها + خلاصه؛ `?fresh=1` برای عبور از کش |

نمونهٔ فیلدهای لینک در پاسخ:

```json
{
  "id": "…",
  "status": "degraded",
  "reasonCode": "jitter",
  "reason": "نوسان تأخیر (۵۲ms) از آستانهٔ مجاز (۴۰ms) بیشتر است.",
  "latencyMs": 24.2,
  "lossPct": 0,
  "jitterMs": 52,
  "capacityMbps": 100,
  "sourceCount": 2,
  "reportingCount": 2,
  "stale": false
}
```

## ۷. آزمون

```bash
# قواعد وضعیت، نوسان و سن داده
node --test server/tests/integration/topology-live.test.mjs

# کمک‌تابع‌های نمایش
npm run test:web
```

آزمون یکپارچه یک دیاگرام واقعی می‌سازد، تجهیزات را به وضعیت‌های مختلف می‌برد و
رنگ/علت لینک را از همان API بررسی می‌کند. همچنین **حذف کامل SNMP** را تضمین
می‌کند: نبود فیلدهای سنجش در پاسخ، حذف مسیر Poll، نبود ستون‌های قدیمی و نبود
جدول `topology_link_telemetry` پس از مهاجرت.
