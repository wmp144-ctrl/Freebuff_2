# مرحلهٔ ۳ — تحلیل وابستگی و تأثیر اختلال

این سند موتور و رابط تحلیل دیاگرام ارتباطات را تعریف می‌کند: شناسایی محل قطع،
تجهیزات وابسته، نقاط بحرانی (Switch/Router/Gateway)، اثر خرابی هر لینک یا
تجهیز و مسیرهای اصلی/پشتیبان.

> اصل حاکم: تحلیل فقط روی **ساختار واقعی ثبت‌شده در دیاگرام** و وضعیت واقعی
> موتور مانیتورینگ انجام می‌شود. گره یا لینکی که در دیاگرام نیست، در نتیجه
> ظاهر نمی‌شود و هیچ مسیر/وابستگی ساختگی ساخته نمی‌شود.

---

## ۱. معماری

```
topology_nodes / topology_links       (ساختار گراف)
topology_links.monitor_device_id + devices  (وضعیت واقعی لینک)
topology_paths                        (مسیرهای اصلی/پشتیبان)
        │
        ▼
server/topology-analysis.js
   BFS چندمنبعی + Tarjan (پل/گره برشی) + شبیه‌سازی حذف
        │
        ▼
GET /topology/diagrams/:id/analysis   Snapshot تحلیلی (فقط خواندنی)
GET /topology/diagrams/:id/impact     شبیه‌سازی قطع یک لینک/گره
        │
        ▼
پنل «تحلیل شبکه» + لایه‌های بوم (رنگ متفاوت مسیر مشکل‌دار، حلقهٔ بحرانی،
برچسب «متأثر» و مسیر اصلی/پشتیبان)
```

- موتور خالص و مستقل از HTTP است؛ هیچ جدول یا حالت جدیدی در Snapshot زنده
  مرحلهٔ ۲ نوشته نمی‌شود.
- همهٔ محاسبات در سرور و روی گراف ذخیره‌شده انجام می‌شود؛ کلاینت فقط انتخاب
  و نمایش می‌کند و نمی‌تواند وضعیت یا وابستگی را دستی تغییر دهد.
- کل مسیر آفلاین است؛ هیچ سرویس بیرونی فراخوانی نمی‌شود.

---

## ۲. مرکز زیرساخت (ریشهٔ تحلیل)

دسترسی هر گره نسبت به «مراکز زیرساخت» سنجیده می‌شود:

1. گره‌های `site` (مرکز تجمع) و `cloud` (ابر/WAN) که حداقل یک لینک دارند.
2. اگر هیچ‌کدام متصل نبود، یک تجهیز با نقش Gateway/Router/Firewall/Core و
   بیشترین اتصال به‌عنوان مرکز **استنتاجی** انتخاب می‌شود.
3. اگر هیچ تجهیزی هم نبود، تحلیل با هشدار «مرکز زیرساخت وجود ندارد» متوقف
   می‌شود؛ هیچ نتیجهٔ ساختگی برگردانده نمی‌شود.

`anchorSource` در پاسخ مشخص می‌کند `explicit` (ثبت‌شده)، `inferred` (خودکار)
یا `none` است. انتخاب خودکار در پنل با هشدار زرد نمایش داده می‌شود.

---

## ۳. الگوریتم‌ها

| تحلیل | روش | معنا |
| --- | --- | --- |
| دسترسی فعلی | BFS چندمنبعی با مسدودکردن لینک‌های `down` و تجهیزات `offline` | تجهیزاتی که همین حالا به هیچ مرکز نمی‌رسند |
| پل (تک‌مسیره) | Tarjan با ریشهٔ مجازی همهٔ مراکز | لینکی که حذفش بخشی از شبکه را از همهٔ مراکز جدا می‌کند |
| نقطهٔ برشی | Tarjan + شمارش زیردرخت | تجهیزی که حذفش تجهیزات پایین‌دست را قطع می‌کند |
| اثر قطع لینک/گره | BFS روی گراف بدون آن مورد | فهرست واقعی تجهیزات و مراکز از دست‌رفته |
| مسیر تا مرکز | BFS با والد هر گره | نمایش «تجهیز ← … ← مرکز» و محل دقیق قطع |
| مسیر جایگزین | وضعیت لینک‌های مسیر اصلی/پشتیبان + نقش فعال | فعال‌شدن خودکار پشتیبان هنگام قطع اصلی |

**نکتهٔ ریشهٔ مجازی:** همهٔ مراکز به یک ریشهٔ مجازی وصل می‌شوند؛ بنابراین
«قطع از دسترسی به هر مرکز» سنجیده می‌شود، نه فقط یک مرکز خاص. اگر دو مرکز
از دو مسیر مستقل در دسترس باشند، حذف یکی از لینک‌های بین آن‌ها دسترسی
تجهیزات را قطع نمی‌کند و به‌درستی «مسیر جایگزین» گزارش می‌شود.

### شدت

شدت بر اساس تعداد تجهیزات متأثر و سهم آن‌ها از تجهیزات دیاگرام:

| شدت | قاعده (تقریبی) |
| --- | --- |
| `critical` | ۱۰ تجهیز یا بیشتر، یا ≥ ۲۵٪ تجهیزات |
| `high` | ۴ تجهیز یا بیشتر |
| `medium` | حداقل ۱ تجهیز |
| `low` | بدون تجهیز وابسته |

اعداد دقیق در `server/topology-analysis.js` تابع `severityOf` تعریف شده‌اند و
UI فقط همان مقدار سرور را نمایش می‌دهد.

## ۴. نقش‌ها و نقاط بحرانی

نقش هر گره به ترتیب از `meta.role`، نوع تجهیز (`deviceType`)، برچسب و نام
تجهیز استنتاج می‌شود: `gateway`، `router`، `switch`، `firewall`، `core`،
`access`، `server`، `site`، `cloud`.

فهرست `criticalNodes` فقط گره‌هایی را نشان می‌دهد که **حداقل یک تجهیز وابسته**
دارند. برای هر مورد:

- `dependentDeviceCount`: تعداد تجهیزات پایین‌دست که با حذف این گره از
  دسترس خارج می‌شوند.
- `dependentNodeCount` و `dependentSiteCount`: گره‌ها و مراکز وابسته.
- `severity` / `severityLabel`: شدت.
- `role` / `roleLabel`: نقش فنی برای تشخیص Switch/Router/Gateway.

`riskyLinks` همهٔ پل‌ها را با تعداد تجهیزات وابسته و شدت برمی‌گرداند. لینکی که
پل نیست در این فهرست نمی‌آید (مسیر جایگزین دارد).

---

## ۵. رخداد فعال و محل قطع

برای هر لینک `down`/`degraded` و هر تجهیز `offline` یک رخداد ساخته می‌شود:

- `label`، `type`، `reason`، دو سر لینک
- `affectedDeviceCount`: تعداد تجهیزات پایین‌دستی که با همین قطع از دسترس
  خارج می‌شوند (با BFS واقعی، نه تخمین).

`live.cutPaths` مسیر واقعی از تجهیز متأثر تا نزدیک‌ترین مرکز را می‌دهد و
`cutLinkId`/`cutNodeId` دقیقاً محل قطع را مشخص می‌کند. بوم این مسیر را با
خط‌چین بنفش و تجهیزات متأثر را با قاب قرمز و برچسب «متأثر» نشان می‌دهد؛
رنگ اصلی لینک همچنان وضعیت سبز/قرمز/زرد/خاکستری مرحلهٔ ۲ را حفظ می‌کند تا
دو معنای رنگی با هم اشتباه نشوند.

حداکثر ۲۰ رخداد و ۱۲ مسیر نمونه در هر پاسخ برگردانده می‌شود؛ شمارش کامل در
`summary` و جزئیات هر مورد از مسیر `impact` قابل دریافت است.

## ۶. مسیرهای اصلی و پشتیبان (Redundancy)

### مدل ذخیره‌سازی

جدول `topology_paths` (Migration ۸):

| ستون | توضیح |
| --- | --- |
| `id` | شناسهٔ متنی یکتا |
| `diagram_id` | دیاگرام (Cascade) |
| `name` | نام گروه؛ اصلی و پشتیبان را به هم وصل می‌کند |
| `role` | `primary` یا `backup` |
| `node_ids` | دنبالهٔ JSON گره‌ها به ترتیب مسیر |
| `link_ids` | لینک‌های استخراج‌شده (برای نمایش/تشخیص شکستگی) |

قواعد:

- هر مسیر حداقل دو گره و حداکثر ۲۵۰ گره دارد؛ گره تکراری مجاز نیست.
- هر دو گرهٔ متوالی باید در همان دیاگرام با یک لینک واقعی وصل باشند.
- در هر گروه حداکثر یک مسیر اصلی و یک مسیر پشتیبان وجود دارد.
- دو سر مسیر اصلی و پشتیبان باید یکی باشند؛ در غیر این صورت «جایگزین»
  معنایی ندارد و سرور با ۴۰۰ رد می‌کند.
- ذخیرهٔ مسیرها مستقل از `revision` گراف است و در یک تراکنش جایگزین می‌شود؛
  دیاگرام قفل‌شده مسیر جدید نمی‌پذیرد (۴۲۳).

### وضعیت مسیر

| وضعیت | معنا |
| --- | --- |
| `up` | همهٔ لینک‌های مسیر فعال |
| `degraded` | حداقل یک لینک اختلال دارد |
| `down` | حداقل یک لینک قطع است یا مسیر شکسته/ناقص است |
| `unknown` | دادهٔ تازه‌ای برای برخی لینک‌ها نیست |

`activeRole` با اولویت «اصلی سالم» محاسبه می‌شود. اگر اصلی سالم نباشد و
پشتیبان `up` باشد، `activeRole = backup`، `failover = true` و مسیر پشتیبان
روی بوم با رنگ بنفش و برچسب «فعال» نمایش داده می‌شود. اگر هر دو مسیر از کار
بیفتند، وضعیت گروه `critical` است.

### ساخت مسیر در رابط کاربری

1. پنل «تحلیل شبکه» را باز کنید.
2. با `Shift` گره‌ها را **به ترتیب** روی بوم کلیک کنید (مثلاً مرکز ← روتر ←
   سوئیچ ← تجهیز مقصد). ترتیب کلیک، ترتیب مسیر است.
3. یک نام گروه وارد کنید (یا نام پیشنهادی دو سر مسیر را بپذیرید).
4. «ذخیره به‌عنوان اصلی» یا «پشتیبان» را بزنید.
5. برای دیدن مسیر روی بوم، دکمهٔ چشم گروه را بزنید. خط آبی/بنفش خط‌چین،
   مسیر اصلی/پشتیبان را نشان می‌دهد.

حذف گروه، هر دو مسیر اصلی و پشتیبان را حذف می‌کند. اگر گره‌ای از گراف حذف
شود، مسیر به‌صورت «شکسته» علامت می‌خورد و هرگز به‌عنوان سالم نمایش داده
نمی‌شود.

## ۷. API

| مسیر | توضیح |
| --- | --- |
| `GET /api/topology/diagrams/:id/analysis` | تحلیل کامل: مراکز، پل‌ها، نقاط بحرانی، رخداد فعال، مسیرها و خلاصه |
| `GET /api/topology/diagrams/:id/impact?linkId=…` | شبیه‌سازی قطع لینک |
| `GET /api/topology/diagrams/:id/impact?nodeId=…` | شبیه‌سازی خرابی تجهیز |
| `GET /api/topology/diagrams/:id/paths` | فهرست مسیرهای ثبت‌شده |
| `PUT /api/topology/diagrams/:id/paths` | جایگزینی کامل مسیرها با اعتبارسنجی |

نمونهٔ کوتاه `impact`:

```json
{
  "target": { "type": "node", "id": "…", "label": "Core-Switch", "role": "switch" },
  "summary": {
    "affectedDeviceCount": 12,
    "downstreamDeviceCount": 11,
    "severity": "critical",
    "alternateRoute": false
  },
  "affected": { "nodeIds": ["…"], "devices": [{ "id": "…", "label": "…", "isTarget": true }] },
  "paths": [{ "pathLabels": ["Access-1", "Edge-Switch", "Core", "مرکز اصلی"], "cutNodeId": "…" }],
  "backupActivated": [{ "name": "مسیر اصلی", "backupStatus": "up" }]
}
```

## ۸. عملکرد و مقیاس

- پیمایش گراف `O(V + E)` است؛ برای ۴۰۰۰ گره و ۸۰۰۰ لینک (سقف مرحلهٔ ۱)
  تحلیل ساختاری در یک گذر Tarjan انجام می‌شود. در سنجش محلی همین اندازه،
  `analyzeTopology` حدود ۶۰ms و شبیه‌سازی تأثیر یک گره حدود ۱۳ms زمان گرفت
  (بدون احتساب خواندن پایگاه‌داده و Snapshot زنده).
- `analysis` در هر بار درخواست محاسبه می‌شود (بدون کش سنگین) و رابط هر ۳۰
  ثانیه آن را تازه می‌کند؛ وضعیت زندهٔ ۱۰ ثانیه‌ای جداست.
- شبیه‌سازی هر لینک/گره فقط با BFS همان مورد انجام می‌شود، نه محاسبهٔ کل
  دیاگرام برای همهٔ حالت‌ها.
- فهرست تجهیزات متأثر در پاسخ به ۲۰۰ مورد و رخدادها به ۲۰ مورد محدود شده‌اند
  تا پاسخ در شبکه‌های بزرگ قابل مدیریت بماند؛ شمارش کامل همیشه موجود است.
- هیچ درخواست شبکه/اینترنتی در تحلیل وجود ندارد.

## ۹. آزمون

```bash
# موتور خالص: پل، نقطهٔ برشی، شدت، مسیر قطع و failover
node --test server/tests/unit/topology-analysis.test.mjs

# API واقعی: ساخت گراف، تحلیل، شبیه‌سازی، اعتبارسنجی و قفل مسیرها
node --experimental-strip-types --test server/tests/integration/topology-analysis.test.mjs

# کمک‌تابع‌های نمایش و لایه‌های بوم
npm run test:web
```

آزمون یکپارچه یک دیاگرام زنجیره‌ای و یک دیاگرام دارای مسیر جایگزین می‌سازد،
قطع لینک را با تجهیز مرجع واقعی ثبت می‌کند و فعال‌شدن مسیر پشتیبان را از همان
API بررسی می‌کند.
