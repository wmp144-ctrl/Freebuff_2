# NetWatch — سامانه پایش، نگهداری و تحلیل زیرساخت شبکه

سامانه‌ی تحت وب و **کاملاً آفلاین** برای مانیتورینگ تجهیزات شبکه از طریق ارسال درخواست Ping در بازه‌های زمانی مشخص، ثبت و ذخیره‌سازی نتایج و تحلیل آن‌ها.

> تمام داده‌ها در یک فایل SQLite محلی ذخیره می‌شود؛ برنامه هیچ ارتباطی با اینترنت یا سرویس ابری ندارد و پس از نصب اولیه به‌صورت کامل آفلاین کار می‌کند.

---

## ۱. اجرای سریع (آفلاین)

نیازمندی: **Node.js نسخه ۲۲٫۱۲ یا بالاتر** (هم برای ماژول داخلی `node:sqlite` و هم حداقل نسخه‌ای که Vite 8 و ابزار ساخت آن می‌خواهند — بدون هیچ وابستگی بومی و بدون نیاز به کامپایل).

```bash
npm install          # فقط یک‌بار (نیاز به اینترنت دارد)
npm run build        # ساخت نسخه تولیدی رابط کاربری
npm start            # اجرای سامانه روی پورت 8787
```

سپس در مرورگر آدرس `http://localhost:8787` را باز کنید. از این مرحله به بعد هیچ نیازی به اینترنت نیست.

| دستور | توضیح |
| --- | --- |
| `npm start` | اجرای کامل سامانه (API + رابط کاربری + موتور مانیتورینگ) روی پورت `8787` |
| `npm run dev` | اجرای حالت توسعه با Vite و HMR روی پورت `3000` |
| `npm run engine` | **اجرای مستقل موتور مانیتورینگ** بدون رابط کاربری |
| `npm run engine -- --once` | یک چرخه بررسی و خروج (مناسب Cron / Task Scheduler) |
| `npm run typecheck` | بررسی نوع‌ها با TypeScript |
| `npm test` | آزمون دود: موتور پایش، زنجیرهٔ قطعی/بازگشت، تجمیع روزانه و مسیرهای API (روی پایگاه‌دادهٔ موقت — به `data/` دست نمی‌زند) |
| `npm run seed:reset` | بازتولید داده‌های نمایشی |

پورت و مقادیر دیگر با متغیرهای محیطی قابل تغییرند:

```bash
PORT=9000 HOST=127.0.0.1 NETWATCH_ENGINE=0 npm start
```

| متغیر | پیش‌فرض | توضیح |
| --- | --- | --- |
| `PORT` | `8787` (تولیدی) / `3000` (توسعه) | پورت سرور |
| `HOST` | `0.0.0.0` | آدرس شنود؛ برای محدودکردن دسترسی فقط به همان دستگاه، `127.0.0.1` بگذارید |
| `NETWATCH_ENGINE` | `1` | با `0` موتور پایش داخل سرور خاموش می‌شود (برای اجرای مستقل موتور) |
| `NETWATCH_DATA_DIR` | `./data` | مسیر پوشه داده‌ها (پایگاه‌داده و نقشه‌ها) |
| `NETWATCH_DB` | `<DATA_DIR>/netwatch.db` | مسیر مستقیم فایل پایگاه‌داده |
| `NETWATCH_SSE_MAX` | `32` | سقف اتصال‌های زندهٔ هم‌زمان (SSE) |
| `NETWATCH_ALLOW_RESET` | `0` | با `1` اندپوینت «بازنشانی داده‌ها» (`POST /api/settings/reset-demo`) فعال می‌شود. پیش‌فرض بسته است؛ برای بازنشانی می‌توانید از `npm run seed:reset` هم استفاده کنید |

> این سامانه برای اجرا در **شبکهٔ داخلی و مورد اعتماد** طراحی شده و احراز هویت ندارد. اگر روی آدرسی می‌شنود که دیگران به آن دسترسی دارند، همهٔ کاربران آن شبکه به داده‌ها و تنظیمات دسترسی خواهند داشت؛ برای اجرای محلی `HOST=127.0.0.1` را تنظیم کنید یا دسترسی را با فایروال محدود کنید.

## ۲. معماری

```
server/                 موتور و API (Node.js + Express)
  db.js                 لایه داده (node:sqlite) + طرح جدول‌ها + داده‌های نمونه
  ping.js               ICMP (ابزار سیستمی ping) / TCP / تشخیص دسترسی
  engine.js             موتور مانیتورینگ، گذار وضعیت، قطعی‌ها، قوانین هشدار، تجمیع روزانه
  engine-cli.js         اجرای مستقل موتور (Headless)
  store.js              دسترسی مشترک به داده‌ها
  impexp.js             ورود/خروج Excel و CSV (SheetJS، محلی)
  mbtiles.js            خواندن نقشه‌های آفلاین MBTiles
  routes/               مسیرهای API
web/                    رابط کاربری (React + Vite + Tailwind + Recharts + Leaflet)
data/                   داده‌های محلی (قابل پشتیبان‌گیری)
  netwatch.db           پایگاه‌داده SQLite
  mbtiles/              فایل‌های نقشه آفلاین .mbtiles
```

**اصل طراحی:** موتور مانیتورینگ کاملاً مستقل از رابط کاربری است. سامانه حتی زمانی که هیچ صفحه‌ای باز نیست بررسی‌ها را ادامه می‌دهد و می‌توان آن را به‌عنوان یک سرویس جداگانه (`npm run engine`) روی سرور اجرا کرد؛ در آن حالت رابط کاربری می‌تواند روی دستگاه دیگری اجرا شود.

### جریان داده

1. موتور در هر چرخه، تجهیزات «سررسیدشده» را بر اساس بازه اختصاصی خودشان انتخاب و با محدودیت همزمانی (پیش‌فرض ۱۲۸) بررسی می‌کند.
2. نتیجه در جدول `samples` ثبت و شاخص‌های تجهیز به‌روزرسانی می‌شود.
3. در صورت شکست متوالی، وضعیت به `Offline` تغییر می‌کند، یک رکورد در جدول `outages` باز می‌شود و هشدار بحرانی ثبت می‌شود.
4. با پاسخ‌های موفق متوالی، وضعیت به `Online`/`Warning` بازمی‌گردد، قطعی بسته می‌شود، هشدارهای پیشین رفع و یک پیشنهاد سابقه تعمیرات ساخته می‌شود.
5. رخدادها به‌صورت زنده (SSE روی `/api/events`) به رابط کاربری اعلام می‌شوند.

## ۳. حالت‌های بررسی (تنظیمات ← موتور مانیتورینگ)

| حالت | توضیح |
| --- | --- |
| `auto` | ابتدا ICMP؛ اگر مجوز RAW socket موجود نبود، خودکار روی TCP سقوط می‌کند |
| `icmp` | فقط ICMP با ابزار سیستمی `ping` |
| `tcp` | اتصال TCP به پورت مشخص (پیش‌فرض ۸۰) — بدون نیاز به مجوز ویژه |
| `simulate` | تولید داده‌های واقع‌نما برای دمو و آموزش (پیش‌فرض نسخه نمایشی) |

### فعال‌سازی ICMP واقعی در لینوکس

اجرای ICMP نیاز به مجوز `CAP_NET_RAW` دارد. اگر سامانه با کاربر غیر ریشه اجرا می‌شود:

```bash
sudo setcap cap_net_raw+ep "$(which ping)"
```

در ویندوز این محدودیت وجود ندارد. در صورتی که ICMP در دسترس نباشد، کارت «وضعیت موتور» در صفحه تنظیمات هشدار می‌دهد و بررسی‌ها روی TCP انجام می‌شود.

برای پایش TCP، پرتی که سامانه بررسی می‌کند از «تنظیمات ← موتور مانیتورینگ ← پورت TCP» خوانده می‌شود (پیش‌فرض ۸۰). تجهیز با یک پاسخ موفق در دسترس نمی‌شود: تا رسیدن به تعداد موفقیت‌های تعیین‌شده در تنظیمات (`successes_for_online`، پیش‌فرض ۲) وضعیت «قطع‌شده» حفظ می‌شود تا نوسان‌های لحظه‌ای، قطعیِ الکی نسازند.

> **حالت پیش‌فرض `simulate` است** تا سامانه بلافاصله با داده‌های واقع‌نما قابل ارزیابی باشد. برای پایش واقعی، در «تنظیمات ← موتور مانیتورینگ» گزینه «خودکار (ICMP/TCP)» را انتخاب کنید.

## ۴. قابلیت‌ها

### داشبورد مدیریتی
- کارت‌های آماری: کل تجهیزات، در دسترس، قطع‌شده، دارای اختلال، هشدارهای فعال، غیرفعال
- شاخص سلامت شبکه (Network Health Score) به‌همراه درجه کیفی، دسترس‌پذیری کل، میانگین تأخیر و میانگین افت بسته
- نمودار وضعیت لحظه‌ای (Donut)، روند تعداد تجهیزات قطع‌شده در ۲۴ ساعت، تعداد قطعی‌ها به تفکیک روز
- ۱۰ تجهیز با بیشترین تأخیر و ۱۰ تجهیز با بیشترین قطعی
- وضعیت گروه‌های تجهیزات، روند شاخص سلامت، فهرست تجهیزات دارای افت کیفیت و آخرین هشدارها

### تجهیزات (Devices)
- نمایش کارتی با نمودار خطی تأخیر یک ساعت گذشته به‌همراه سایه زیر نمودار؛ در این نمودار خط‌چین آستانهٔ پینگ رسم می‌شود، بخش‌های پایین آستانه سبز، بخش‌های بالای آستانه نارنجی و بازه‌های بی‌پاسخ (قطعی) قرمز نمایش داده می‌شوند
- انتخاب تعداد کارت‌های هر ردیف (۱ تا ۸) از یک جعبهٔ کوچک کنار حالت نمایش؛ انتخاب در حافظهٔ مرورگر ذخیره می‌شود
- فیلتر وضعیت به‌صورت سه بخش کنار هم (در دسترس / قطع‌شده / همه) و در صورت وجود تجهیز با تأخیر بیشتر از آستانه، دکمهٔ «پینگ بالا» با شمارش
- فهرست گروه‌ها در منوی کناری با تعداد کل، وصل و قطع هر گروه؛ «همه گروه‌ها» در ابتدای فهرست
- نمایش جدولی حرفه‌ای با جست‌وجو، فیلترهای پیشرفته، مرتب‌سازی، صفحه‌بندی، تأخیر و افت بسته
- ارسال Ping لحظه‌ای، پنجرهٔ شناور پینگ زنده، ویرایش، حذف و ورود به صفحه جزئیات
- عملیات گروهی: فعال/غیرفعال‌سازی تجهیز و پایش، انتقال گروه، تغییر بازه بررسی، افزودن تگ، Ping و حذف
- افزودن تجهیز، تشخیص IP تکراری و اعتبارسنجی آدرس IP (IPv4/IPv6/نام هاست)
- ورود گروهی از Excel/CSV با پیش‌نمایش، گزارش خطاها و تشخیص IPهای تکراری
- خروجی Excel/CSV از تجهیزات و از مختصات جغرافیایی

### صفحه جزئیات هر تجهیز
- **بخش اول — اطلاعات عمومی:** نام، آدرس IP، نوع تجهیز، گروه، محل استقرار، وضعیت فعلی، زمان آخرین بررسی
- **بخش دوم — اطلاعات مانیتورینگ:** وضعیت Online/Offline، زمان آخرین Ping، Response Time، کمترین/بیشترین/میانگین تأخیر، Packet Loss، تعداد Ping موفق و ناموفق، Consecutive Failures، Uptime، زمان آخرین قطعی، مدت قطعی فعلی، MTBF و MTTR
- **بخش سوم — نمودارهای تاریخی:** نمودار Latency در ۱ ساعت / ۶ ساعت / ۲۴ ساعت / ۷ روز / ۳۰ روز، نمودار Packet Loss، نمودار وضعیت Online/Offline و نمودار Availability — هر نمودار با انتخاب‌گر بازه مستقل
- **بخش چهارم — تاریخچه اختلالات:** زمان شروع، زمان پایان، مدت قطعی، علت اختلال و اقدام ثبت‌شده، همراه با جدول آخرین نمونه‌های ثبت‌شده

### مدیریت تعمیرات و نگهداری
- **فقط سوابقی که کاربر ثبت می‌کند نگهداری می‌شود؛** قطعی‌های شناسایی‌شدهٔ موتور مانیتورینگ به‌صورت خودکار سابقهٔ تعمیرات نمی‌سازند (تاریخچهٔ قطعی‌ها در بخش هشدارها و صفحهٔ تجهیز در دسترس است)
- ثبت علت خرابی (مشکلات زیرساخت فیبر نوری، مشکلات شبکه، قطعی برق، هنگ کردن سوئیچ، سوختن یا خرابی تجهیز و سایر دلایل قابل تعریف)
- ثبت اقدام انجام‌شده (تعویض تجهیز، تعمیر تجهیز، تعویض قطعه، اصلاح زیرساخت، رفع مشکل شبکه و سایر اقدامات)
- تاریخ و زمان شروع و پایان، مدت قطعی، تکنسین، هزینه و توضیحات تکمیلی
- پنجره‌های تعمیرات (Maintenance Window) روزانه/هفتگی برای توقف بررسی در زمان سرویس

### نقشه شبکه (Network Map)
- **فهرست تجهیزات در سمت چپ نقشه و هم‌ارتفاع با آن** (عرض کمتر از نقشه) با امکان نمایش/مخفی‌کردن از نوار ابزار
- **جانمایی با کشیدن و رها کردن:** در حالت ویرایش موقعیت، تجهیز را از فهرست بکشید و روی نقطهٔ دلخواه نقشه رها کنید
- نمایش تجهیزات روی نقشه با رنگ بر اساس وضعیت و پالس برای تجهیزات قطع‌شده
- ثبت و ویرایش موقعیت روی نقشه با کلیک، و ورود/خروج مختصات از فایل Excel
- **علامت‌های نقشه:** تعریف نوع علامت (مثلاً «تجهیز در حال نصب» با رنگ و آیکن دلخواه)، جانمایی چند نمونه از آن با یک «نام مشخص» و مختصات جغرافیایی، جابه‌جایی و ویرایش، و خروجی گرفتن از نام و مختصات
- **ورود و خروج علامت‌ها** با فرمت مشخص (Excel/CSV) به‌همراه **فایل نمونهٔ آماده** از مسیر `/api/markers/template`
- مدیریت لایه‌ها: ایجاد لایه، نمایش/مخفی‌سازی، تعیین لایه پیش‌فرض و **بارگذاری نقشه آفلاین `.mbtiles`**
- **پشتیبانی از هر دو نوع MBTiles:** کاشی‌های تصویری (Raster) با Leaflet و کاشی‌های برداری (Vector/PBF-MVT) با MapLibre GL — تشخیص خودکار بر اساس متادیتای فایل و استایل‌سازی خودکار لایه‌های برداری
- سرو کاشی‌ها از فایل MBTiles به‌صورت آفلاین از مسیر `/api/tiles/&lt;layerId&gt;/z/x/y`
- در صورت نبود فایل MBTiles، یک لایه پایه وکتور داخلی نمایش داده می‌شود (بدون هیچ درخواست اینترنتی)

### سیستم هشدار و اعلان
- اعلان زنده هنگام **قطع و وصل شدن** تجهیز (هشدارهای `offline` و `recovery` به‌همراه اعلان مرورگر)
- **پنجرهٔ شناور پینگ زنده:** با زدن دکمهٔ «پینگ زنده» روی هر تجهیز، پنجرهٔ شناوری باز می‌شود که هر یک ثانیه پاسخ تجهیز را می‌گیرد و کمینه/بیشینه/میانگین تأخیر و افت بسته را نشان می‌دهد؛ می‌توان **چندین پنجره** برای چند تجهیز باز کرد (فهرست کارتی در گوشهٔ سمت چپ صفحه، تا ۸ پنجره، قابل جمع‌کردن)
- **لاگ قطع و وصل تجهیزات** به دو صورت نمودار زمانی و فهرست جزئیات رویدادها
- **نمودار قطعی‌های هم‌زمان** (تشخیص قطعی هم‌زمان چند تجهیز و بازه‌های اشتراکی)
- **خط زمانی (Timeline) قطعی‌ها** برای هر تجهیز در بازهٔ انتخابی
- **آمار تجهیزات پرقطعی** (تعداد قطعی، مجموع مدت قطعی و آخرین قطعی هر تجهیز)
- تعریف سطوح اهمیت (اطلاع / هشدار / بحرانی)
- تعریف قوانین هشدار بر پایه متریک‌های قطع دسترسی، تأخیر، افت بسته و بازگشت به حالت عادی
- تعیین تأخیر قبل از ثبت هشدار، فاصله ضد تکرار (جلوگیری از هشدار تکراری) و محدوده گروه
- بازه‌های زمانی سکوت هشدار (Alert Suppression) با قابلیت غیرفعال‌سازی
- تاریخچه کامل هشدارها، هشدارهای فعال، بررسی‌شده و رفع‌شده + عملیات گروهی و اعلان زنده در رابط کاربری

### گزارش‌گیری و تحلیل
- بازه‌های ۲۴ ساعت، ۷، ۳۰ و ۹۰ روز با فیلتر گروه، تگ و تجهیز
- شاخص‌های کل: دسترس‌پذیری، میانگین و بیشترین تأخیر، تعداد قطعی‌ها، مجموع مدت قطعی، MTTR
- روند روزانه دسترس‌پذیری و تأخیر، قطعی‌ها به تفکیک روز، علت‌های قطعی و اقدامات نگهداری
- جدول تفصیلی هر تجهیز (تعداد بررسی، موفق/ناموفق، دسترس‌پذیری، تأخیر، افت بسته، قطعی، MTTR، MTBF، هشدار) با مرتب‌سازی
- خروجی CSV و Excel از گزارش

### تنظیمات
- **عمومی:** نام سامانه، تقویم شمسی/میلادی، اختلاف زمانی نمایش، بازه پیش‌فرض نمودارها، اعلان‌ها
- **موتور مانیتورینگ:** حالت بررسی، بازه Ping، Timeout، تعداد تلاش مجدد، تعداد Packet، حداکثر همزمانی، آستانه تأخیر، آستانه افت بسته، شکست متوالی برای Offline، پاسخ موفق متوالی برای Recovery، پورت TCP
- **نمایش و نقشه:** مرکز و زوم پیش‌فرض، برچسب تگ‌ها
- **گروه‌ها و تگ‌ها:** مدیریت کامل با شمارش تجهیزات و وضعیت
- **لایه‌های نقشه:** مدیریت لایه‌های آفلاین (تصویری و برداری)
- **چیدمان ویجت‌ها:** تعیین ترتیب نمایش بخش‌های صفحهٔ جزئیات تجهیز و داشبورد، افزودن/حذف ویجت و تغییر ابعاد هر ویجت (کوچک / متوسط / بزرگ / تمام‌عرض)
- **علت‌ها و اقدامات:** افزودن/حذف علت‌های خرابی و اقدامات قابل ثبت
- **داده‌ها:** مدت نگهداری رکوردها، مسیر پایگاه‌داده، بازنشانی داده‌های نمونه
- کنترل موتور (شروع/توقف/بازراه‌اندازی)، بررسی همه تجهیزات و مشاهده لاگ رویدادها

## ۵. ورود گروهی از Excel / CSV

ستون‌های قابل شناسایی (نام‌های فارسی و انگلیسی هر دو پذیرفته می‌شوند):

| ستون | معادل انگلیسی |
| --- | --- |
| نام تجهیز | `name` |
| آدرس IP | `ip` |
| نام هاست | `hostname` |
| نوع تجهیز | `type` / `device_type` |
| گروه | `group` |
| محل استقرار | `location` |
| ساختمان / رک | `building` / `rack` |
| عرض و طول جغرافیایی | `latitude` / `longitude` |
| سازنده، مدل، سریال، مسئول | `vendor`, `model`, `serial`, `owner` |
| اولویت | `priority` (کم / عادی / بالا / بحرانی) |
| تگ‌ها | `tags` (جدا‌شده با کاما) |

قالب آماده از دکمه «قالب Excel» در پنجره ورود گروهی یا از مسیر `/api/devices/template?format=xlsx` قابل دریافت است. در حین ورود، آدرس‌های نامعتبر، IPهای تکراری (در فایل و در سیستم) و مختصات نامعتبر تشخیص داده و گزارش می‌شوند.

> ورود CSV هم با BOM (خروجی خود سامانه و «CSV UTF-8» اکسل) و هم بدون BOM (ذخیرهٔ معمولی ویرایشگرهای متن) خوانده می‌شود؛ متن فارسی در هر دو حالت درست تفسیر می‌شود.

## ۷. پایگاه‌داده

تمام داده‌ها در `data/netwatch.db` (SQLite) ذخیره می‌شوند:

`devices`، `groups`، `tags`، `device_tags`، `samples` (رکوردهای خام)، `outages`، `daily_stats` (تجمیع روزانه)، `alerts`، `alert_rules`، `maintenance_records`، `maintenance_windows`، `map_layers`، `marker_types`، `map_markers`، `settings`، `engine_log`.

- رکوردهای خام پس از مدت `retention_days` (پیش‌فرض ۱۴ روز) به‌صورت خودکار حذف می‌شوند؛ آمار روزانه برای تحلیل بلندمدت باقی می‌ماند.
- **پشتیبان‌گیری:** کافی است فایل `data/netwatch.db` را کپی کنید.

### مقیاس‌پذیری

طراحی برای پایش پایدار حداقل ۱۰۰۰ تجهیز:

- **زمان‌بندی صریح:** هر تجهیز ستون `next_check_at` دارد و هر چرخه فقط تجهیزات سررسیدشده با ایندکس خوانده می‌شوند (نه پیمایش کل جدول در هر ثانیه). بازهٔ واقعی بررسی برابر بازهٔ تنظیم‌شده است (خطای کمتر از یک‌چهارم ثانیه).
- **محدودیت همزمانی** قابل تنظیم (`max_workers`، پیش‌فرض ۱۲۸) و اولویت‌محور (بحرانی → کم).
- **تجمیع روزانه** هر ۵ دقیقه و به‌صورت چند پرس‌وجوی گروهی انجام می‌شود؛ روزهای جا‌مانده (مثلاً پس از خاموشی سرور) در شروع برنامه خودکار بازسازی می‌شوند.
- **گزارش‌های بلندمدت** (بیش از یک روز) روزهای کامل را از جدول `daily_stats` می‌خوانند، پس با بزرگ‌شدن تاریخچه کند نمی‌شوند؛ فقط روز جاری از نمونه‌های خام محاسبه می‌شود.
- **هرس دوره‌ای تکه‌تکه** (۵٬۰۰۰ رکورد در هر گام) تا یک حذف بزرگ، نوشتن موتور را قفل نکند.
- مرز روزها، نیمه‌شب **محلی** (بر پایهٔ `timezone_offset_minutes`) است تا با نمودارها و برچسب‌های رابط کاربری یکسان باشد.
- مصرف حافظه ثابت است و رابط کاربری فقط بازه‌های مورد نیاز را با تجمیع (Bucketing) درخواست می‌کند.

## ۸. نکات فنی رابط کاربری

- تم روشن با گرادیان‌های ظریف آبی و زرد، پس‌زمینه سفید مایل به خاکستری، کارت‌های با گوشه‌های گرد (۱۴ تا ۲۲ پیکسل)، سایه‌های بسیار ملایم و استفاده محدود از Glassmorphism
- تایپوگرافی Vazirmatn (بومی‌سازی‌شده و آفلاین) و آیکون‌های یکپارچه Lucide
- چیدمان راست‌به‌چپ، تقویم شمسی با قالب‌بندی بومی و اعداد فارسی
- انیمیشن‌های ظریف، Hover Effect و به‌روزرسانی زنده از طریق SSE
- طراحی کاملاً Responsive برای دسکتاپ، تبلت و موبایل با یکپارچگی Design System در همه صفحات
- کتابخانه‌های نمودار (Recharts) و نقشه (Leaflet) به‌صورت بومی نصب می‌شوند و هیچ درخواستی به CDN یا سرویس خارجی ارسال نمی‌شود
- بستهٔ برنامه به چند تکه تقسیم شده است: `react`، `recharts` و `leaflet` جداگانه‌اند و برگهٔ نقشه (و Leaflet) فقط هنگام ورود به نقشه بارگذاری می‌شود

## ۹. امنیت و سخت‌سازی

این برنامه یک ابزار درون‌شبکه است؛ نکات زیر برای روشن‌بودن وضعیت امنیتی آمده است.

**آنچه اعمال می‌شود**

- **گارد مبدأ (Same-Origin):** درخواست‌های تغییردهندهٔ داده (`POST`/`PUT`/`PATCH`/`DELETE`) با هدر `Origin` بیگانه رد می‌شوند (۴۰۳)؛ این کار جلوی سوءاستفادهٔ سایت‌های دیگر از سرویس درون‌شبکه (CSRF) را می‌گیرد. کلاینت‌های غیرمرورگری (curl، اسکریپت، موتور مستقل) `Origin` نمی‌فرستند و مسدود نمی‌شوند.
- **هدرهای امنیتی:** `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy` و در حالت تولیدی `Content-Security-Policy` سخت‌گیرانه (فقط `self`، بدون اسکریپت خارجی).
- **اعتبارسنجی تنظیمات:** همهٔ مقادیر ورودی در یک نقطه مرزگذاری می‌شوند (مثال: `ping_interval` حداقل ۵ ثانیه، `max_workers` حداکثر ۵۱۲، `retention_days` حداقل ۱ روز تا ناخواسته کل تاریخچه حذف نشود). مقدارهای ردشده در پاسخ `rejected` و در گزارش رویدادها ثبت می‌شوند.
- **محدودسازی ورودی‌ها:** بدنهٔ JSON حداکثر ۲ مگابایت، پارامترهای Ping دستی مرزگذاری‌شده (تعداد بسته و زمان انتظار)، سقف ۵۰٬۰۰۰ ردیف برای ورود گروهی، بررسی **پیش از نوشتن** برای پسوند `.mbtiles` و کنترل فضای آزاد دیسک (حداقل ۲۵۶ مگابایت) هنگام بارگذاری نقشه.
- **بازنشانی داده‌ها پیش‌فرض غیرفعال است:** اندپوینت `POST /api/settings/reset-demo` کل پایگاه‌داده را پاک می‌کند؛ چون سامانه احراز هویت ندارد، تا وقتی اپراتور صریحاً `NETWATCH_ALLOW_RESET=1` را تنظیم نکند، درخواست بازنشانی با پاسخ `403` رد می‌شود و هیچ رکوردی خوانده یا حذف نمی‌شود.
- **عدم افشای جزئیات:** خطاهای داخلی سرور تنها در گزارش رویدادها ثبت می‌شوند و پیام عمومی به کلاینت برمی‌گردد.
- **سقف اتصال‌های زنده:** بیش از `NETWATCH_SSE_MAX` اتصال SSE پذیرفته نمی‌شود (پاسخ ۵۰۳) تا چند تب باز یا کلاینت ناشناس حافظهٔ سرور را تمام نکند.
- **پایداری فرآیند:** خطاهای مهارنشده (خطای همگام و Promise ردشده) ثبت می‌شوند و فرآیند با خاموش‌سازی مرتب (بستن پایگاه‌داده) پایان می‌یابد؛ پورت اشغال‌شده پیام گویا می‌دهد.

**آنچه در برنامه وجود ندارد (و باید در نظر بگیرید)**

- **احراز هویت و نقش‌ها:** هیچ ورود کاربری وجود ندارد. هر کسی که به آدرس سرویس دسترسی داشته باشد می‌تواند داده‌ها را تغییر دهد. راه‌حل پیشنهادی: `HOST=127.0.0.1` و دسترسی از طریق SSH Tunneling، یا قرار دادن سرویس پشت یک پروکسی با احراز هویت و HTTPS در همان شبکه.
- **HTTPS:** خود سرور TLS ندارد؛ اگر نیاز دارید، از Reverse Proxy (nginx/Caddy) استفاده کنید.
- **محدودیت نرخ درخواست:** برای شبکهٔ مورد اعتماد طراحی شده و Rate Limit ندارد.

آسیب‌پذیری‌های شناخته‌شدهٔ وابستگی‌ها با `npm audit` قابل بررسی است؛ پس از ارتقای زنجیرهٔ ساخت به Vite 8 (که esbuild را کنار گذاشته) خروجی کامل `npm audit` **بدون مورد** است، هم در وابستگی‌های اجرایی و هم در ابزارهای ساخت.
